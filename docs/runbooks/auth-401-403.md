# Runbook — Auth 401/403

## Síntoma

- Un endpoint protegido responde `401 Unauthorized`.
- Un usuario autenticado responde `403 Forbidden` en una operación que esperaba poder ejecutar.
- Swagger UI o el cliente principal falla al invocar recursos protegidos.

## Cómo reproducir

1. Intentar `GET /api/references` sin JWT.
2. Repetir la misma llamada con JWT válido.
3. Probar un recurso ajeno con `GET /api/references/{id}` o `DELETE /api/references/{id}`.
4. Repetir desde Swagger UI si el problema solo aparece ahí.

## Qué mirar primero

- ¿El JWT existe y llega en el header correcto?
- ¿La ruta está cubierta por la allowlist o debería estar protegida?
- ¿La denegación es por no autenticado, por rol insuficiente o por ownership?
- ¿El entorno actual expone Swagger/OpenAPI como se esperaba? (solo público en dev/test desde Fase 2 semanas 1-3, ADR-013)

## Logs y eventos esperados

- `event=auth.login.failed` si el problema nace en autenticación.
- `event=authorization.denied` con `correlationId`, `path` y motivo, si la denegación es por rol (`AccessDeniedHandlerImpl`).
- Respuesta de error coherente con la política `401`/`403`/`404` documentada (ADR-014).
- El mismo `correlationId` aparece en el header de respuesta `X-Correlation-Id` y en cada línea de log de esa request.

## Causas probables

- JWT ausente, expirado o inválido.
- `SecurityFilterChain` abrió o cerró una ruta incorrectamente.
- `@PreAuthorize` contradice la regla de URL.
- La política de ownership no coincide con lo que espera el cliente.
- Swagger UI no tiene `SecurityScheme` configurado o el token no se aplicó.
- Rate limit excedido en `/signin` o `/refresh-token` (devuelve `429`, no `401`/`403` — no confundir).

## Cómo resolver

1. Confirmar si el fallo es de autenticación (401) o de autorización (403).
2. Revisar logs con el mismo `correlationId` desde filtro, handler y controller.
3. Verificar la matriz de permisos y la política de ownership.
4. Reproducir con test o request mínima antes de tocar código.
5. Si hay regresión, buscar el último estado verde y considerar `git bisect`.

## Cómo prevenir que vuelva a ocurrir

- Mantener tests de autorización y ownership para la ruta afectada.
- No mezclar cambios de `SecurityFilterChain` con cambios funcionales grandes.
- Documentar cualquier decisión de `403` vs `404` en `docs/decision-log.md`.
