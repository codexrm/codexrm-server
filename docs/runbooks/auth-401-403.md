# Runbook — Auth 401/403

## Symptom

- A protected endpoint responds `401 Unauthorized`.
- An authenticated user gets `403 Forbidden` on an operation they expected to be able to run.
- Swagger UI or the main client fails when calling protected resources.

## How to reproduce

1. Try `GET /api/references` without a JWT.
2. Repeat the same call with a valid JWT.
3. Try someone else's resource with `GET /api/references/{id}` or `DELETE /api/references/{id}`.
4. Repeat from Swagger UI if the problem only appears there.

## What to check first

- Does the JWT exist and does it arrive in the right header?
- Is the route covered by the allowlist, or should it be protected?
- Is the denial due to no authentication, insufficient role, or ownership?
- Does the current environment expose Swagger/OpenAPI as expected? (only public in dev/test since Phase 2 weeks 1-3, ADR-013)

## Expected logs and events

- `event=auth.login.failed` if the problem starts in authentication.
- `event=authorization.denied` with `correlationId`, `path` and reason, if the denial is due to role (`AccessDeniedHandlerImpl`).
- Error response consistent with the documented `401`/`403`/`404` policy (ADR-014).
- The same `correlationId` appears in the `X-Correlation-Id` response header and in every log line of that request.

## Likely causes

- Missing, expired or invalid JWT.
- `SecurityFilterChain` opened or closed a route incorrectly.
- `@PreAuthorize` contradicts the URL rule.
- The ownership policy does not match what the client expects.
- Swagger UI has no `SecurityScheme` configured or the token was not applied.
- Rate limit exceeded on `/signin` or `/refresh-token` (returns `429`, not `401`/`403` — do not confuse them).

## How to resolve

1. Confirm whether the failure is authentication (401) or authorization (403).
2. Review the logs with the same `correlationId` from the filter, handler and controller.
3. Check the permission matrix and the ownership policy.
4. Reproduce with a test or a minimal request before touching code.
5. If there is a regression, find the last green state and consider `git bisect`.

## How to prevent recurrence

- Keep authorization and ownership tests for the affected route.
- Do not mix `SecurityFilterChain` changes with large functional changes.
- Document any `403` vs `404` decision in `docs/decision-log.md`.
